§2系統架構

四個區域:VPN、你的 Windows 主機、Ubuntu 虛擬機、產生回答的 LLM。VM 裡的服務都跑在 Docker 上,其中 Portainer 是獨立容器,其他五個屬於 rag-openwebui 這組 stack。使用者不論從 VPN 或主機,都經過 nginx 這個唯一入口進 Open WebUI。Open WebUI 是中心,負責切文件、呼叫 embedding、查向量庫、把結果交給 LLM。

  • 平常的資料流
  • 經 VPN 連進來
  • 同步程式處理檔案時才走;主機 GPU 連不到就用 VM 的 CPU
  • 備用路徑

Docker 的幾個名詞

這套系統所有服務都跑在 Docker 上。先分清楚下面幾個名詞,後面看 Portainer 時會用到。

名詞是什麼在這套系統裡
Docker Engine在 VM 上建立、執行、管理容器的程式VM 系統服務 docker
Image(映像檔)唯讀的「安裝包」,內含程式和它需要的環境,本身不會執行nginx、pgvector/pgvector:pg15、ollama/ollama、python:3.12-slim、自建的 open-webui-soffice、portainer-ce
Container(容器)用 image 跑起來的執行個體,彼此隔離。刪掉重建後,容器內的暫存內容會消失6 個:nginx、open-webui、postgres、ollama、rag-sync、portainer
Volume放在容器外面的資料保存區,容器刪掉重建,資料還在openwebui-data、pgdata、portainer_data
Stack用一份 docker-compose.yml 描述的一組容器:一起啟動、一起停止,共用一個內部網路,容器之間用名稱互相連線rag-openwebui,含其中 5 個容器
Network容器之間的虛擬網路rag-openwebui_default(stack 內)、bridge(Portainer)

從屬關係是:VM 裡有 Docker Engine,Docker Engine 管理 image、container、volume 和 network;stack 是把其中幾個 container 編成一組。Portainer 本身也是容器,但不在 stack 裡:它靠掛進來的 /var/run/docker.sock 控制 Docker Engine。不放進 stack,是因為在 Portainer 按「停止 stack」時,不能把操作介面自己也停掉。能連上 Portainer 並登入的人,等同可以在 VM 上以最高權限做任何事。

  • 啟動、掛載的方向
  • VM 的資料夾掛進容器(圖中以 rag-sync 為例,其他資料夾也各自掛進對應容器)

§3資料流程

提問時

  1. 你在 Open WebUI 提問輸入 # 選 AIVM_DB_Test 知識庫
  2. 問題轉成向量VM 的 Ollama bge-m3,約 1 秒
  3. pgvector 找出最相近的段落HNSW 索引,預設取前 3 段
  4. 段落 + 問題送給 LLM雲端 LLM,這一步資料會離開你的電腦
  5. 回答附上引用來源可點引用看原文段落

日常同步(每 15 分鐘)

  1. 掃描共用資料夾9,672 個檔案約 18 秒
  2. 計算 SHA-256依大小與修改時間快取,沒變的檔案不重算
  3. 重新產生檔案目錄依前兩層資料夾分組,共 43 份
  4. sync/diff 比對知識庫Open WebUI 官方 API,找出新增、更新、刪除
  5. 處理差異先擷取文字,再逐批加入知識庫(下方兩階段)
  6. 清掉殘留沒連進知識庫的舊版本、重複或中斷的上傳紀錄會被刪除

處理檔案:兩階段

直接用 Open WebUI 的「上傳到知識庫」會把 CSV 每一行切成一段(一個 CSV 常有 3,000 段),而且每段算兩次向量。同步程式改成先擷取全文、再交給知識庫統一切成 1,000 字一段,每段只算一次,所有檔案的切法一致。

  1. 切換 embedding 到主機 GPU主機連不到就用 VM 的 Ollama;處理完一定切回
  2. 重用已擷取的檔案同一路徑、同一內容之前擷取過但還沒連上的,直接拿來用,不重新上傳
  3. 階段 A:擷取文字少量新檔走一般上傳;一次 200 個以上暫停 embedding 只抽文字(較快,但暫停期間提問會異常,所以只在大量時用)。讀不出文字的掃描檔記錄下來,檔案沒變就不重試
  4. 階段 B:逐批加入知識庫每 8 個檔案一批、一次送一批,送完核對每個檔案確實連上
  5. 暫時性錯誤自動重試例如主機 Ollama 重啟:等 30、60、120 秒重試;GPU 連不到就改用 VM 繼續。還是失敗的留到下一輪,不會重傳

Ollama 在做什麼

Ollama 是在自己電腦上跑 AI 模型的服務程式:它載入模型檔,再開一個 API 讓其他程式呼叫。這套系統有兩個 Ollama,一個在 VM 的容器裡,一個在 Windows 主機上用顯示卡(選用,VM 連得到才用)。它們做三件事,其中兩件用 bge-m3 這個 embedding 模型,把一段文字轉成 1,024 個數字(向量)。意思相近的文字,向量的方向也相近,所以「U.2 Gen5 連接器規格」和「SFF-8639 PCIe5 量測報告」用字不同也找得到彼此。

項目VM 的 Ollama主機的 Ollama
位置VM 容器 ollama,位址 ollama:11434(只在容器網路內)Windows,位址 <主機 IP>:11434(只開給 VMware 虛擬網路)
硬體VM 的 CPU(4 核)GTX 1060 6GB,走 Vulkan
模型bge-m3(embedding)、qwen2.5:3b(本地 LLM)bge-m3
什麼時候用每次提問;主機連不到時也負責處理檔案rag-sync 處理新增或修改的檔案時(連得到才用)
速度約 0.7 段/秒;一個問題 0.1–0.5 秒約 2.4 段/秒
重要設定OLLAMA_KEEP_ALIVE=24h,模型常駐記憶體,提問不用等載入OLLAMA_HOST=<主機 IP>:11434、OLLAMA_LLM_LIBRARY=vulkan

Open WebUI 呼叫 Ollama 時一次送 16 段、同時最多 2 個請求。

從 VPN 使用

VM 用 VPN 用戶端連上 VPN 後,有 VPN 連線權限的人在自己的電腦開 http://<VM 的 VPN IP> 就會經 nginx 進 Open WebUI。VM 的 VPN IP 看 VM 的網路資訊,VPN 連上後多出來的那張網卡就是。

要確認的事說明
VPN 允不允許連入有些 VPN 只允許用戶端往外連,不允許其他 VPN 使用者連回來。連上後要實測,不行就要請 VPN 管理者開放。
VPN 對既有連線的影響全通道(full tunnel)模式可能讓主機暫時連不到 VM 的 <VM IP>,也可能讓 VM 連雲端 LLM 的流量改走 VPN 而被擋。連上後要實測。
只留 nginx 對外目前 3000、5432、9000 也綁在所有網路介面上。資料庫與 Portainer 的連接埠也對外開放,而 Portainer 等同 VM 的 root 權限,開放 VPN 連線前建議改成只限 VM 本機。
帳號管理VPN 使用者註冊後預設是「待審核」,要你在管理員控制台 → 使用者核准。不想讓人自行註冊可以在管理員控制台關閉註冊。
傳輸加密nginx 目前是 HTTP。VPN 通道本身有加密;若需要 HTTPS,要另外申請憑證設定 nginx。

§6決策與限制

項目說明
vLLM 沒有部署VM 沒有 GPU,VMware Workstation 也不能把顯卡給 VM 跑 CUDA。等有 GPU 的主機再加。
資料外流範圍建索引全在本機。提問時被找出的段落會經 OpenRouter 送到你選的模型廠商。
OpenRouter 額度沒有指定輸出上限時,OpenRouter 會用模型的最大輸出(例如 65,536 token)預估費用,超過 key 的剩餘額度就直接拒絕(requires more credits, or fewer max_tokens)。解法擇一:到 OpenRouter 加值或調高這把 key 的額度上限;或在管理員控制台 → 設定 → 模型 → 選模型 → 進階參數,把「最大 Token 數」設成 4096 之類的值。
掃描型 PDF63 個 PDF 和 1 個 PPTX 沒有文字層,內容搜不到,只能用檔名從檔案目錄找到(會標示「無法擷取文字」)。要讀內容需要另外加 OCR。
CSV 與試算表內容會串成全文再每 1,000 字切一段,不是一行一段。查特定數值時,用檔名或測項名稱一起問比較準。
工程資料檔S 參數、板檔、壓縮檔、Cadence 與 HFSS 專案檔是數字矩陣或二進位,放進全文只會污染搜尋,所以只進檔案目錄。
舊版資料夾全部納入,新舊版本內容可能互相矛盾,提問時可指定版本或年份。
主機 GPU 速度Vulkan 實測 2.4 段/秒,已是這張卡的上限;批次大小與並行數都不影響。
處理速度依賴主機主機要開機並登入,Ollama 才會啟動。連不到時自動退回 VM CPU(約 0.7 段/秒)。目前這台 VM 連不到主機,一律用 VM 的 CPU。
主機 Ollama 拒絕連線首次建庫時約 90 個檔案沒建成,錯誤是主機 Ollama「拒絕連線」。查證後它其實沒當掉,是 Open WebUI 預設不限制同時請求數,一批 CSV 一次丟出上百個請求把連線塞爆。已把同時請求數限制為 2;同步程式也會核對每個檔案,沒連上的下一輪直接重連,不會漏。

§7疑難排解

現象先看這裡
網頁打不開Portainer → Containers,確認 open-webui 是 running;看它的 Logs
Portainer 打不開,但 Open WebUI 正常多半是 Docker 的 docker0 網路被關掉。在 VM 終端機重啟 Docker 服務,所有容器會自動重啟,約 1 分鐘後恢復
open-webui 一直重開,Logs 有 maintenance_work_mem 或 No space left on device建向量索引的記憶體不夠,確認 §5「PostgreSQL 設定」兩個參數還在
rag-sync Logs 出現「暫時失敗…秒後重試」多半是 embedding 失敗(open-webui 的 Logs 會有 Ollama embed error),會自動重試;「留待下輪」的檔案下一輪直接重連,不用處理。經常發生時,確認管理員控制台 → 設定 → 文件的 embedding 同時請求數還是 2
聊天出現 requires more credits, or fewer max_tokensOpenRouter 額度不夠,見 §6「OpenRouter 額度」
同步處理檔案期間提問很慢提問的 embedding 和建索引共用同一張 GPU,會排在後面。處理完就恢復(平常 0.1–0.5 秒)
新放的檔案搜不到等 15 分鐘或重啟 rag-sync;確認格式在全文清單內;看 rag-sync Logs 有沒有「失敗」
rag-sync 出現 401API key 失效:網頁重新產生,更新 /srv/rag-sync/.env,重啟 rag-sync
大量建庫說主機 GPU 連不到主機 Ollama 有沒有在跑(系統匣圖示);防火牆規則是否存在。若 VM 不在主機的 VMware 虛擬網路上,連不到是正常的,會自動改用 VM 的 CPU
提問完全不引用知識庫管理員控制台 → 設定 → 文件,確認「略過 embedding 與檢索」是關閉的(rag-sync 每輪也會自動關閉)
共用資料夾看不到VMware 的共用資料夾設定是否啟用;rag-sync 掃到 0 個檔案時會停下,不會刪除任何資料
